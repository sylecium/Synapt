# Rapport d'audit de code - Synapt (2026-09-18)

## 1. Cartographie

- **Architecture** : Application desktop Linux locale monoposte (Debian 13) associant un backend natif Rust (Tauri 2) et une interface web Svelte 5 / SvelteKit SPA (`adapter-static`, sans SSR).
- **Backend Rust** : Moteur Tauri 2 (`src-tauri/src/lib.rs`), commandes IPC (`commands.rs`), base SQLite locale rusqlite monoposte (`db.rs`, `repo.rs`), gestion documentaire et PDF printpdf (`honoraires.rs`, `honoraires_pdf.rs`), intégrations réseau HTTPS (`stripe.rs`, `ntfy.rs`).
- **Frontend Svelte** : Svelte 5 (runes `$state`, `$derived`, `$effect`), Tailwind CSS 4, shadcn-svelte (Bits UI), éditeur riche Tiptap (`src/routes/`, `src/lib/components/`).
- **Gestionnaire de paquets** : Bun pour le frontend (`package.json`, `bun.lock`), Cargo pour le backend (`src-tauri/Cargo.toml`).
- **Points d'entrée** : `src-tauri/src/main.rs` (binaire natif), `src/routes/+layout.svelte` (shell UI, sidebar, bandeau de mise à jour, interception fermeture).
- **CI / Distribution** : GitHub Actions (`.github/workflows/release.yml`) produisant un paquet Debian signé (`.deb`) avec auto-mise à jour via `tauri-plugin-updater` et `tauri-plugin-process`.

## 2. Priorisation

Les 20 % du code concentrant 80 % des risques techniques, métiers et légaux sont :
1. **Cycle de vie de l'application et persistance des notes** (`src-tauri/src/lib.rs`, `+layout.svelte`, `RdvPanel.svelte`, `debouncedNoteSave.ts`) : fermeture de l'application, interception d'événements fenêtre, intégrité des notes cliniques saisies.
2. **Synchronisation externe et fuseaux horaires** (`ntfy.rs`, `commands.rs`, `repo.rs`) : planification et exactitude des rappels envoyés au praticien.
3. **Accès base de données et cohérence des requêtes** (`db.rs`, `repo.rs`, `honoraireRdv.ts`) : requêtes SQL, canonicalisation des dates, requêtes N+1 IPC résiduelles.
4. **Persistance de la configuration et des secrets** (`settings.rs`, `commands.rs`) : atomicité des fichiers JSON, gestion des clés Stripe et tokens ntfy.

## 4. Analyse approfondie et fiches d'anomalies

### Problème 1 : Blocage total de la fermeture de la fenêtre par `prevent_close` sans appel à `destroy()`
- **Sévérité** : Critique
- **Emplacement** : `src-tauri/src/lib.rs:43-47` et `src/routes/+layout.svelte:19-24`
- **Constat** : Côté Rust, l'événement `WindowEvent::CloseRequested` exécute inconditionnellement `api.prevent_close()`. Côté Svelte, le callback `win.onCloseRequested` attend le flush des notes en mémoire (`flushAllDebouncedNotes()`), mais n'invoque jamais `win.destroy()` ni `exit()`.
- **Impact** : L'utilisateur ne peut pas fermer l'application en cliquant sur le bouton de fermeture de la fenêtre ("X") ni via le raccourci Alt+F4 de son environnement de bureau Linux. L'application reste bloquée à l'écran et exige un arrêt forcé (SIGINT / SIGTERM / `kill`).
- **Correction proposée** :
Dans `src/routes/+layout.svelte` :
```diff
 				unlisten = await win.onCloseRequested(async () => {
-					await Promise.race([
-						flushAllDebouncedNotes(),
-						new Promise((resolve) => setTimeout(resolve, 1500))
-					]);
+					try {
+						await Promise.race([
+							flushAllDebouncedNotes(),
+							new Promise((resolve) => setTimeout(resolve, 1500))
+						]);
+					} finally {
+						await win.destroy();
+					}
 				});
```
- **Effort** : S

### Problème 2 : Décalage horaire UTC/Local dans les notifications de rappel ntfy
- **Sévérité** : Majeur
- **Emplacement** : `src-tauri/src/ntfy.rs:41-45`
- **Constat** : Dans `ReqwestNtfy::for_rdv`, l'horodatage `debut` (de type `DateTime<Utc>`) est formaté directement avec `debut.format("%d/%m %H:%M")` sans conversion dans le fuseau horaire local de la machine.
- **Impact** : Pour un praticien exerçant en France métropolitaine, le message ntfy reçu sur son téléphone mobile affiche l'heure UTC : un rendez-vous planifié à 14h00 indique 12h00 en heure d'été (CEST, UTC+2) ou 13h00 en heure d'hiver (CET, UTC+1). Risque direct d'erreur de consultation pour le praticien.
- **Correction proposée** :
Dans `src-tauri/src/ntfy.rs` :
```diff
+        let local_debut = debut.with_timezone(&chrono::Local);
         let (title, message, priority) = match kind {
             RappelKind::H24 => (
                 "Rappel RDV demain".to_string(),
                 if client_nom.is_empty() {
-                    format!("RDV le {}", debut.format("%d/%m %H:%M"))
+                    format!("RDV le {}", local_debut.format("%d/%m %H:%M"))
                 } else {
-                    format!("RDV avec {} le {}", client_nom, debut.format("%d/%m %H:%M"))
+                    format!("RDV avec {} le {}", client_nom, local_debut.format("%d/%m %H:%M"))
                 },
                 4,
             ),
```
- **Effort** : S

### Problème 3 : Risque de perte de notes cliniques dans le panneau RDV lors de la fermeture
- **Sévérité** : Majeur
- **Emplacement** : `src/lib/components/RdvPanel.svelte:196-240`
- **Constat** : `RdvPanel.svelte` implémente son propre système de sauvegarde différée (timer manuel de 400 ms et fonction `flushNote()`), sans s'enregistrer auprès de `createDebouncedNoteSave()`. Lors de la fermeture de la fenêtre, seul `flushAllDebouncedNotes()` est déclenché dans `+layout.svelte`.
- **Impact** : Si le praticien rédige ou modifie une note de consultation dans le volet latéral d'un rendez-vous et ferme la fenêtre dans les 400 ms suivantes, cette note n'est pas prise en compte par le flush global et les modifications saisies sont perdues.
- **Correction proposée** :
Refactoriser l'enregistrement de note de `RdvPanel.svelte` pour utiliser l'utilitaire commun `createDebouncedNoteSave` (qui s'enregistre automatiquement dans `activeFlushes` et dispose d'une méthode `destroy()` sur `onDestroy`), ou exposer et connecter explicitement son flush au registre central.
- **Effort** : M

### Problème 4 : N+1 requêtes IPC séquentielles dans `findHonoraireEmisForRdv`
- **Sévérité** : Majeur
- **Emplacement** : `src/lib/honoraireRdv.ts:4-18`
- **Constat** : Pour déterminer si un rendez-vous possède une note d'honoraires émise (lors de l'ouverture du menu contextuel), `findHonoraireEmisForRdv` récupère la liste complète des honoraires du client via IPC (`honorairesList(clientId)`), puis interroge individuellement chaque note (`honorairesGet(h.id)`) dans une boucle synchrone pour inspecter ses lignes.
- **Impact** : Pour un client régulier ayant 20 ou 30 séances facturées, l'ouverture du menu contextuel ou du panneau déclenche 20 à 30 appels IPC consécutifs vers SQLite, entraînant des latences et des saccades dans l'interface.
- **Correction proposée** :
Ajouter une commande Rust dédiée retournant directement l'honoraire actif lié à un `rdv_id` en une seule requête SQL indexée :
```sql
SELECT h.id, h.numero, h.statut, ...
FROM honoraires h
JOIN honoraire_lignes l ON l.honoraire_id = h.id
WHERE l.rdv_id = ?1 AND l.actif = 1 AND h.statut = 'emise'
LIMIT 1;
```
- **Effort** : S

### Problème 5 : Écriture non atomique et écrasement silencieux par les valeurs par défaut de `settings.json`
- **Sévérité** : Majeur
- **Emplacement** : `src-tauri/src/settings.rs:141-174`
- **Constat** :
  1. `save_settings` tronque et réécrit directement `settings.json` sur le disque sans passer par un fichier temporaire suivi d'un renommage atomique (`std::fs::rename`).
  2. `load_settings` utilise `serde_json::from_str(&contents).unwrap_or_default()`.
- **Impact** : En cas de coupure de courant, de crash ou d'arrêt brutal pendant `save_settings`, le fichier `settings.json` est corrompu ou vide. Au redémarrage suivant, `load_settings` réinitialise silencieusement tous les réglages du cabinet (nom, SIRET, adresse, clé Stripe, topic ntfy) aux valeurs par défaut sans aucun message d'erreur ni sauvegarde de secours.
- **Correction proposée** :
Écrire d'abord dans un fichier temporaire `settings.json.tmp`, appeler `sync_all()`, puis effectuer un remplacement atomique via `std::fs::rename`. Conserver une copie de sauvegarde `settings.json.bak` en cas d'erreur de désérialisation.
- **Effort** : S

### Problème 6 : Absence de migration pour canonicaliser les dates historiques des RDV
- **Sévérité** : Mineur
- **Emplacement** : `src-tauri/src/repo.rs:775-783, 790-805` et `src-tauri/src/db.rs:248-255`
- **Constat** : Le filtrage par plage temporelle en SQL repose sur une comparaison lexicographique (`rdv.debut >= ?1 AND rdv.debut < ?2`) en supposant le format canonique strict UTC `%Y-%m-%dT%H:%M:%S+00:00`. Les bases issues des versions antérieures (v0.1.3/v0.1.4) peuvent contenir des chaînes avec suffixe `Z` ou avec millisecondes (`.000Z`). Aucune instruction `UPDATE` n'a été ajoutée dans `migrate()` pour normaliser les données existantes.
- **Impact** : Risque d'omettre des rendez-vous existants ou de fausser les bornes lors de l'affichage de l'agenda et du dashboard si la base SQLite contient un historique antérieur au lot d'optimisation.
- **Correction proposée** :
Ajouter une migration unique dans `migrate()` normalisant la colonne `debut` de la table `rdv` vers le format canonique UTC.
- **Effort** : S

### Problème 10 : Risque de désérialisation IPC `null` sur saisie de durée tarif
- **Sévérité** : Suggestion
- **Emplacement** : `src/routes/tarifs/+page.svelte:66`
- **Constat** : Lors de la soumission d'un tarif, `duree_minutes: Number.parseInt(dureeMinutes, 10)` produit `NaN` si le champ est vide ou mal formé. Dans l'envoi JSON vers Tauri, `NaN` devient `null`, ce qui déclenche une erreur de désérialisation brute du backend Rust (`invalid type: null, expected i64`) au lieu d'un message de validation clair.
- **Impact** : Message d'erreur technique affiché au praticien s'il valide un champ durée vide.
- **Correction proposée** :
Valider la saisie côté client avant l'appel IPC : `const duree = Number.parseInt(dureeMinutes, 10); if (!duree || duree <= 0) ...`.
- **Effort** : S

### Problème 11 : Absence de flush des notes avant le redémarrage par l'updater
- **Sévérité** : Suggestion
- **Emplacement** : `src/lib/components/UpdateBanner.svelte:54`
- **Constat** : La méthode `install()` invoque `await relaunch()` dès que le téléchargement et l'installation sont achevés, sans forcer la persistance des notes actives en attente (`flushAllDebouncedNotes()`).
- **Impact** : Si une mise à jour est déclenchée pendant que le praticien termine la saisie d'une note, le redémarrage immédiat coupe le processus avant la fin de la temporisation.
- **Correction proposée** :
Ajouter `await flushAllDebouncedNotes();` immédiatement avant `await relaunch()`.
- **Effort** : S

## 6. Les 5 actions prioritaires

1. **Rétablir la fermeture de l'application (P1)** : Ajouter l'appel à `await win.destroy()` dans le bloc `finally` de `onCloseRequested` dans `+layout.svelte`. Sans cette correction, l'application est impossible à quitter normalement sous Linux.
2. **Corriger le fuseau horaire des rappels ntfy (P2)** : Convertir l'horodatage UTC en heure locale (`with_timezone(&Local)`) avant de formater le message de rappel ntfy. Évite au praticien d'avoir des horaires décalés de 1 à 2 heures sur son téléphone.
3. **Sécuriser la sauvegarde des notes du panneau RDV (P3)** : Intégrer la sauvegarde des notes de `RdvPanel.svelte` dans le registre de `createDebouncedNoteSave` afin de garantir qu'aucune note de consultation n'est perdue à la fermeture.
4. **Supprimer le N+1 résiduel des honoraires (P4)** : Remplacer la boucle de requêtes `honorairesGet` côté client par une commande Rust mono-requête `honoraire_get_for_rdv(rdv_id)`.
5. **Rendre l'écriture des réglages atomique (P5)** : Sécuriser la persistance de `settings.json` via écriture temporaire et renommage atomique pour immuniser les données du cabinet contre toute corruption en cas de coupure inopinée.

## 7. Problèmes structurels transverses

- **Coordination du cycle de vie de fermeture** : L'interception de la fermeture a été divisée entre Rust (`prevent_close`) et le frontend (`onCloseRequested`) sans que le contrat de destruction effective ne soit verrouillé. Un protocole clair doit être maintenu : Rust prévient la fermeture immédiate, le frontend synchronise ses tâches asynchrones, puis déclenche explicitement la destruction de la fenêtre.
- **Gestion des fuseaux horaires entre persistance et notification** : La base de données stocke des dates canoniques UTC, ce qui est une bonne pratique. Cependant, la frontière vers les canaux humains (SMS, notifications ntfy, affichage textuel) doit systématiquement opérer une conversion explicite en heure locale pour éviter des confusions d'horaires.
- **Frontière de responsabilité entre SQL et IPC** : Malgré les optimisations récentes, plusieurs composants frontend continuent d'exécuter des jointures logiques ou des calculs d'agrégation (recherche de correspondance RDV/honoraire, décompte du nombre de clients ou de tarifs) en transférant des collections complètes sur le bus IPC. SQLite doit être privilégié pour toutes les opérations de jointure et d'agrégation.

- **Flux Stripe réel avec webhook** : La configuration Stripe a été analysée au niveau de la génération des Payment Links HTTPS, mais aucune transaction avec carte bancaire réelle n'a été exécutée.
- **Paquetage Debian en conditions réelles** : L'installation physique via Polkit (`dpkg -i`) n'a pas été déclenchée sur la machine hôte pendant cet audit.
